# Phase 2 Persistence Correctness

Status: Phase 2 in progress; validation/payroll and Banking persistence slices verified on both providers. Phase 1 parent: cbf373b. This record distinguishes implemented work from verified closure.

## First implementation slice

- Check-off validation stages detached rows and batch changes before the transactional commit. Employment reads are filtered by tenant/employer/active status and requested payroll identifiers, in chunks of 500. Payroll identifiers are opaque case-sensitive values; duplicate input rows or ambiguous employment matches are rejected, not arbitrarily selected. Invalid amount/batch totals cannot validate. Successful validation execution persists diagnostics even when its Data validity flag is false.
- CheckOff now applies the existing tenant/soft-delete filter helper. PostgreSQL bytea concurrency values are generated by the application; SQL Server retains database rowversion. No columns or types were added. Mapping metadata and provider regression verification are required before closure.
- Payroll executes in one transaction, loads PAYE bands, and selects configuration no later than the Nairobi payroll-month end or current time, whichever is earlier. EffectiveDate, CreatedAt and Id establish deterministic ordering. Inputs are filtered before materialization and employee components are indexed once.
- Existing payslips are preserved. Re-running a processed period is rejected until an explicit correction workflow exists. Missing/ambiguous salaries and invalid components reject the run rather than silently skipping employees. ProcessedAt doubles as a portable optimistic concurrency token, preventing two runs from both committing.
- Generic transaction failure clears staged entities before the context can be reused; rollback uses a cleanup token independent of cancelled application work.
- Three resolved payroll ERR001 entries were removed from the exact architecture register; the baseline was not expanded.

## Banking persistence slice - 2026-09-12

Savings deposits now explicitly stage existing detached account balances. First deposits stage the new account and transaction using the domain-assigned ID and call CompleteAsync once, removing the earlier empty-account commit. Withdrawals explicitly stage the deducted balance, including the fee. Both savings notification calls now receive the request CancellationToken.

Fixed-deposit withdrawals check affordability including the flat penalty before changing the tracked account or staging a penalty transaction. Insufficient funds therefore leave no penalty for a later save to accidentally commit. Exact-balance successful withdrawals still save both the penalty and withdrawal.

Local Docker is now available. All 16 focused Phase2PersistenceTests passed locally on PostgreSQL and SQL Server, including eight new provider cases: successive deposits plus fee-bearing withdrawal verified from fresh contexts; publication failure during the first deposit leaves no committed account/transaction; rejected early withdrawal followed by CompleteAsync preserves balance and has no transactions; and exact-balance withdrawal persists both records. The test fixture uses the real Banking context, repositories, Unit of Work and MediatR handlers. No database model or migration changes were required for this slice.

This establishes single-save persistence, not durable accounting delivery or safe duplicate execution. Existing savings notifications remain in-process and precede the save. No outbox, receiver deduplication, PostgreSQL savings concurrency repair or background tenant scope is claimed. Those remain prerequisites for durable check-off dispatch; Phase 2 remains in progress.

Banking-slice pre-PR checks: API build passed, all 43 unit tests passed and all 84 architecture tests passed. The architecture debt register was unchanged.

## Retry, interest and provider-context corrections - 2026-09-12

- ExecuteInTransactionWithRetryAsync now propagates CancellationToken through the EF execution strategy, transaction begin/save/commit and backoff. Invalid retry arguments fail before work. Failed attempts clear tracked state, roll back using an independent cleanup token and preserve the original exception, including on the last attempt. Transactions are disposed before waiting. The ordinary transaction strategy also receives the token.
- All 13 existing HR/IAM retry call sites pass their request token. Redundant CompleteAsync calls inside retry callbacks were removed. Expected failure envelopes still permit intentional writes to commit: this preserves security revocations and validation diagnostics. Callback authors must re-read mutable state on every retry; existing IAM callbacks that capture entities and wider identity-manager transaction boundaries still require review.
- Savings and deposit accounts persist nullable LastInterestAccruedOn dates. Interest jobs use the existing UTC-day convention, capture the date once per invocation and skip dates already accrued. They do not infer past balances or backfill missed days. Savings retains two-decimal rounding; deposit accrual explicitly rounds to its four-decimal storage precision.
- Interest and maturity jobs commit at most 200 accounts per transaction and re-read within each retry. Per-account exception swallowing was removed. Failed batches roll back; previously committed batches remain, and their persisted dates make the next invocation skip them. Deposit accrual excludes matured accounts; maturity capitalization clears accrued interest in the same transaction as its transaction record. A competing update cannot capitalize the same interest twice.
- Banking generates PostgreSQL bytea RowVersion values on writes, preserving existing column types and SQL Server-generated rowversion. Fresh detached balance updates now detect competing commits on both providers.
- Both CheckOff provider subclasses now pass ICurrentTenantProvider, ICurrentActorProvider and logging dependencies into the base context. Previously, production DI selected subclasses that silently dropped these dependencies even though base-context tests supplied them. Provider-specific DI tests verify audit stamping and isolation from another tenant.
